## Rischi e alternative

| Rischio | Impatto | Alternativa / mitigazione |
|---|---|---|
| Vitest carica `vite.config.ts` e avvia il bridge IWSDK | test lenti o che aprono processi | `vitest.config.ts` dedicato (T0.2); se il plugin si carica comunque, lanciare con `--config vitest.config.ts` nello script |
| Interop `ajv` / `ajv-formats` ESM-CJS in Vitest | import che falliscono | `import Ajv from 'ajv'` e `addFormats.default ?? addFormats`; in alternativa `createRequire` |
| Playwright/Chromium headless non installato per `dev up --ai-mode agent` | gate 3 bloccato | `npx playwright install chromium` (chiedere all'utente se serve rete/sudo); in subordine `--ai-mode collaborate` con finestra visibile (annunciarlo) |
| Porta 8081 occupata | `dev up` fallisce senza spostarsi | `npx @iwsdk/cli dev down`, poi riprovare; se non basta, trovare il processo con `ss -ltnp` |
| `defineAssets({})` rifiutato | build rotta dopo la pulizia | un solo asset minimo procedurale al posto del vuoto (da verificare con `iwsdk-reference`) |
| **Parametri URL non raggiungibili dagli strumenti MCP** | tutti gli scenari con `?house=...` non eseguibili | non è un problema di M0 ma lo diventa in M1: gli strumenti `browser_*` non navigano a URL arbitrari ("This tool does not navigate to arbitrary URLs"). Soluzione pianificata in `M1.md` T1.2 (file di override solo-sviluppo). Da verificare in alternativa `--allow-browser-automation` di `dev up` |
| La CI su GitHub non si può provare dal PC | gate 4 solo statico | l'utente fa il primo push e conferma il verde; fino ad allora è "verificato staticamente" nel report |
